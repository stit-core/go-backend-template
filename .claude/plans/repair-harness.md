# repair-harness — точная обвязка, живой жизненный цикл шаблона, совместный повторный аудит

## Цель
Третья, завершающая часть программы исправлений по аудиту. Проза обвязки становится точной,
непротиворечивой и проверяемой машиной; форки получают улучшения шаблона — общие машинные правила
версией golibinfra, остальное штатным git-способом; prune не ломает проект. Итог программы
подтверждается совместным повторным аудитом шаблона и golibinfra в объёме программы: каждый угол
≥ 9/10.

  контракт ошибок API, покрытие ≥ 90%.

  handoff или бэклог.

- Создание и push тегов шаблона без OK владельца.

## Решения
- Доставка обновлений в форки: поведенческие инварианты держат сами киты (fail-closed, порядок
  хуков, явные публичные операции), общие правила раскладки и лесенку миграций — версия golibinfra
  (`archkit`, хелпер testkit); проза, скиллы, скрипты, Makefile, lint-конфиг и тесты обвязки —
  git-способом (дифф путей шаблона между тегами). Своего движка синхронизации, плагинов скиллов и
  `go run`-инструментов нет.
- `archkit` — только правила, общие для раскладки сервисов stit; allowlist и module path — у
  потребителя; правило ужесточается minor-версией с шагом миграции в аннотации тега.
- Повторный аудит — той же рубрикой и теми же экспериментами, иначе оценки несравнимы; golibinfra
  — рубрикой базового аудита китов, на том теге, который шаблон отдаёт в форки.
- Решения владельца (29.09): теги обвязки шаблона создаются и пушатся (Q1); auth и user — гибрид:

  неиспользуемую директиву только у включённого линтера. Директивы разбираются из комментариев
  `go/ast` по правилам golangci-lint (пробелы, регистр, пояснение после `//`), список включённых —
  `golangci-lint linters` и `formatters --json`, пустой или без бинаря — FAIL. Проверка текстом в
  `lint.sh` не годится: ловит строки и прозу, теряет пробелы, регистр и форматтеры, молча
  проходит при сбое `git grep`. Мёртвых директив в дереве нет.
- S1: спросить некого — пункт «Сначала спросить» вне задачи или плана хаба уходит вопросом в отчёт,

- S6: версия обвязки — `.template/version` в самом шаблоне (коммит выпуска несёт тег с тем же
  именем — `TestTemplatePaths` держит это на push тега): форк получает её при создании, перенос
  сдвигает её как любой путь шаблона. Первый перенос — от коммита шаблона по дереву первого

- S6: перенос — `git diff` путей шаблона между версиями → `git apply -3`: конфликты в индексе, как у
  merge. Module path шаблона в Go-файлах переноса заменяется на module path форка в обеих версиях

  удалённый шаблоном файл, который форк менял, не трогаются и называются (`git apply` атомарен).

- S6: «канон шаблона» в `make status` — тег версии в истории и module path тега (валидатор, N4):
