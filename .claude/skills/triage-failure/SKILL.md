# Skill: triage-failure

**Шаг 0** — прочитай инструментом Read `.claude/rules/tests-pipeline.md`: багфикс начинается с теста.

Дисциплинированный разбор падения. Цель — найти корневую причину, не замазать симптом, и зафиксировать инвариант тестом.

**Red-арм cockpit'а:** `smartdev` переключает сюда, когда `make status` дал `ATTENTION:` (build, sqlc-drift, migrations, lint), `make check` или тест красный, или задача — багфикс. Багфикс идёт сюда, а не в `plan`: его ведёт строгая петля RED→GREEN→REFACTOR. Фича-работа тоже дефолтно тест-first (ведёт `smartdev §4`), но её разбор отказов — здесь.

## Когда применять

- Красный тест, lint или build
- Юзер кидает stack trace / panic / error message или описывает баг

## Когда НЕ применять

- Новая возможность, а не падение — маршрут по таблице «Маршрут задачи» (CLAUDE.md).
- Лёгкая опечатка которую видно с первой строки — просто чини, не разводи процедуру.

## Категории падений

| Тип | Признаки | Где смотреть |
|---|---|---|
| **Build** | `cannot find package`, `undefined: ...`, `cannot use ... as ...` | `make build` — первая ошибка обычно главная |
| **Lint** | `golangci-lint` сообщения с `(linter)` в конце строки; `FAIL: golangci-lint exit N` — линтер не отработал | `make lint` — по строке на замечание, `FORMAT=detailed` — все, со строками кода |
| **Unit test** | `--- FAIL: Test<Name>`, assertion failure | `make test PKG=<pkg> FORMAT=detailed` |
| **Integration test** | падает только под `make test-int` | проблемы в БД-state, миграциях, testcontainers |
| **Race** | `WARNING: DATA RACE` | `go test -race -run Test<Name>` — стек двух горутин |
| **Panic** | `goroutine N [running]: …` | nil-deref / index OOB / closed channel |
| **Drift** | `make gen-check` падает | сгенерированный код не пересобрали после правки источника (`make gen`) |

## Шаги

### 1. Воспроизвести минимально

Спроси юзера или посмотри сам:
- Как воспроизводится? Команда?
- На какой ветке / коммите?
- Когда последний раз работало?

Если воспроизводится локально — гоняй точечно, не `make test` на всём:
```bash
go test -run Test<Name> -count=1 ./path/to/pkg
go test -race -run Test<Name> -count=10 ./path/to/pkg   # для flaky/race
```

### 2. Прочитать сообщение целиком

Не первую строку — целиком. В Go-выводе обычно:
- Заголовок: что упало
- Stack trace или diff between expected / got
- "Tests:" сводка

Часто полезное — в середине, после длинного стек-трейса. Читай до конца.

### 3. Сформулировать гипотезу

Одно предложение: "X падает потому что Y" — проверяемое.

Примеры:
- "TestRefresh_ReusedToken падает потому что MarkUsed не идемпотентен относительно дубликатов в одной транзакции"
- "build падает потому что после миграции NNNN sqlc не перегенерирован — старая сигнатура в repository.go"
- "lint forbidigo падает потому что добавили `slog.Info` в новом файле — нужно logkit"

Если гипотез несколько — выбирай самую дешёвую в проверке.

### 4. TDD для багфиксов (обязательно)

Если это баг (а не build/lint/drift):

1. **Напиши падающий тест**, воспроизводящий баг.
   - Имя: `Test<Behavior>` или `Test<Method>_<Scenario>`.
   - Тест должен падать по той же причине что и production-баг — иначе ты тестируешь что-то другое.
2. `go test -run Test<Name> ./pkg` → red. Подтверди что red — твой red, не тестовая инфра.
3. Только теперь правь продакшен-код.
4. `go test -run Test<Name> ./pkg` → green.
5. `make test PKG=./pkg` → весь пакет green (не сломал соседние тесты).
6. Коммит: оба файла одним `fix(<scope>): <one-liner>`; в теле — строка красного прогона из п. 2
   (`--- FAIL: Test<Name> …`), чтобы RED-first был виден в истории, и строка `Review:` (CLAUDE.md
   § Готово).

### 5. Не-баг-флоу (build / lint / drift / race)

| Случай | Действие |
|---|---|
| **Build error** после правки sqlc-запроса | `make gen` — проверь, что сигнатура в `infra/postgres/db/*.sql.go` обновилась. Если нет — посмотри запрос в `queries/*.sql`, синтаксис аннотации `-- name: X :one\|many\|exec\|execrows`. |
| **Build error** после правки `.mockery.yml` или интерфейса | `make gen` — мок-файл регенерится. |
| **forbidigo** | замени `fmt.Print*` / `log.*` / `print(ln)` / `slog.*` / запись в `os.Stdout`/`os.Stderr` на `logkit.Logger`. Внутри тестов forbidigo выключен — если падает в тесте, путь не `*_test.go`. |
| **archtest** (`TestLayout` — вызов `archkit` — и др.) | граница домена или слоя: чужой домен — port + adapter (skill `scaffold`, вариант port); сообщение теста называет правило. |
| **errcheck** | `_ = unhandledErr` — нет; разбери err-возврат и обработай. `//nolint` — ослабление гейта: только по явной просьбе юзера (CLAUDE.md § Границы). |
| **gosec G115** | int-конверсия с потенциальным overflow — добавь явную проверку границы. `repository.go` доменов уже исключён в `.golangci.yml` (версия — PG int4); новое исключение — только по явной просьбе юзера. |
| **Race detector** | прочти оба стека целиком; найди shared state без синхронизации. Минимальный фикс — sync.Mutex или channel; идеальный — устрани shared state. |
| **mocks drift** (`make gen-check`) | `make gen` локально, закоммить дельту. Если в `*_test.go` остались устаревшие EXPECT'ы — обнови. |
| **sqlc drift** (`make gen-check`) | `make gen`, проверь дельту в `infra/postgres/db/*`, закоммить. |
| **openapi drift** (`TestOpenAPISpec`, `make gen-check`) | `make gen`: `openapi.json` — контракт API; дельта показывает, что поменялось в операциях и схемах, закоммить её вместе с кодом. |

### 6. Если корневая причина в чужом коде

- golibinfra баг → не лечи у себя workaround'ом: путь — `docs/reference/architecture.md § Граница с golibinfra` (план в golibinfra → тег → bump).
- Тест чужой библиотеки flaky → не маркируй `t.Skip()`. Проверь, не глобальное ли state'овое загрязнение.

### 7. Когда застрял

Признаки:
- 2+ попытки фикса не помогли.
- Каждая попытка ломает другие тесты.
- Гипотеза не сужается.

Действия:
1. Откатись (`git stash`) к чистому red-state.
2. Сформулируй вслух (юзеру): "Я думаю, что X, но проверка через Y показывает Z. Не хватает информации Q."
3. Делегируй встроенному сабагенту `Explore`: "найди все места, где валидируется/вызывается <function>" — он вернёт сжатую сводку.
4. Если всё равно — пиши план через `plan` skill: TDD-research-spike.

### 8. Верификация фикса

```bash
make test PKG=./pkg                  # на свой пакет
make lint PKG=./pkg                  # на свой пакет
go test -run Test<Name> -count=20 ./pkg   # для flaky — 20 прогонов подряд
```

Готово и коммит — по CLAUDE.md § Готово.

## Что искать дополнительно

Когда нашёл фикс, спроси себя:
- Не пропущен ли тест на смежный сценарий? (если баг был в edge case A, есть ли B рядом?)
- Не баг ли это паттерна? (если в одном domain'е пропущена валидация, нет ли её в других?)
- Стоит ли добавить инвариант в `policy_test.go` / `entity_fuzz_test.go`?

## Anti-patterns

- ❌ "Перепиши тест чтобы он проходил" — это сокрытие, не фикс.
- ❌ `t.Skip()` для flaky — корневая причина не уйдёт, появится в проде.
- ❌ `--no-verify` чтобы запушить красное — заблокировано `permissions.deny`, и правильно.
- ❌ Замазать ошибку через `if err != nil { return nil }` без обоснования.
- ❌ Фикс без теста для баг-фикса. TDD не опциональна для багов.
- ❌ Большой "while we're at it" — расширение скоупа когда чинишь баг. Баг-фикс = маленький коммит. Большое — отдельный план.
