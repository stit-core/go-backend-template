# Skill: infra-handoff

**Шаг 0** — прочитай инструментом Read `.claude/rules/infra-impact.md`: его таблица решает, инфра-изменение ли это.

Процедура фиксации инфра-затрагивающего изменения. Зона репо — код→image; всё, что требует действия инфра-стороны, должно уйти в хаб `<org>/infra` явным структурированным сообщением, а не остаться в голове. Правило-якорь — `.claude/rules/infra-impact.md`; этот skill — как именно оформить и куда положить.

## Когда применять

- `make status` → `== Infra-touch ==` не `none` (cockpit чейнит сюда)
- Правишь файл под `paths:` правила `infra-impact` — его таблица решает, инфра-изменение ли это
- Юзер спрашивает, задевает ли изменение инфру или нужен ли новый секрет

## Когда НЕ применять

- Чисто внутренняя логика/тесты/рефактор без смены env/контракта/зависимостей
- Code-default тюнинг без нового **обязательного** ENV (дефолт в коде → инфре делать нечего)
- Уже оформлен актуальный блок для этого же изменения — не дублируй

## Шаги

### 1. Классифицировать изменение

Определи класс по таблице `.claude/rules/infra-impact.md`. Если ни один — это не инфра-изменение, выходи.

### 2. Определить действие инфра-стороны

- **проект** (`<org>/infra`): compose `environment:` / `.env` (required env и секреты — значение проект кладёт в окружение, не коммитит), новый сервис-зависимость в compose, scaling, доставка infra-репо на VPS (`make ship`).
- **registry** (image push) и выкатка тега (`make bump`) — зона skill `release`, не этого блока.

### 3. Сформировать блок

```
=== INFRA HANDOFF · передай инфра-админу ===
WHAT   <имя/тип, default, required?>
WHY    <фича/причина — коммит/шаг плана>
ACTION <конкретное действие инфра-стороны>
WHO    <проект (compose env / .env)>
DECIDE <нужно решение админа (значение/выбор) или «дефолт N ок?»>
RISK   <последствие бездействия>
===
```

Конкретно. `WHAT: env HTTP_RATE_LIMIT_RPS, default 50, optional` — годится. `WHAT: что-то с rate limit` — нет. Значение секрета **не** писать (только имя ключа + «нужен»; `.claude/rules/env-local.md`).

### 4. Положить так, чтобы доехало до релиза

- **Хаб:** пришёл агентом из `<org>/infra` — блок входит в твой итоговый отчёт хабу. Прямой заход — покажи блок юзеру и попроси передать в `<org>/infra` (из этого репо это не делается).
- **Накопитель:** допиши блок в `.claude/plans/handoff.md` (строку `_пусто_` — убери) тем же коммитом, что изменение — есть активный план или нет. `make release` печатает накопитель в финальный INFRA-HANDOFF и очищает коммитом; что уйдёт, видно заранее: `make release VERSION=vX.Y.Z DRY_RUN=1`.

### 5. Граница

Не выполняй `make bump` / `make ship` / `ssh <vps>` / правки чужого репо. Роль — сформировать и отдать сообщение. Дальше — хаб `<org>/infra`.

## Anti-patterns

- ❌ Пометить инфра-задачу «готово»/закоммитить без предъявленного блока.
- ❌ «Допишу на релизе» — release агрегирует уже записанное; не записал в накопитель → потеряно.
- ❌ Значение секрета в блоке/чате (только имя ключа).
- ❌ Размытый WHAT/ACTION без конкретики — админ не сможет принять решение.
- ❌ Самому деплоить / править чужой репо — чужая зона, чужие креды.
- ❌ Гнать блок на не-инфра-правку (шум обесценивает сигнал).
