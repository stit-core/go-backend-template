# Skill: plan

Долгосрочный планировщик. Применяется когда задача больше "правка одного файла" и юзер хочет сначала разложить её на атомы, ответить на открытые вопросы, и только потом отпустить агента работать.

Файлы плана живут в `.claude/plans/`. `roadmap.md` — индекс активных задач. `<slug>.md` — детальный план одной задачи. И индекс, и файлы задач — committable, видны команде, ревьюются в PR.

## Когда применять

- "Распиши план для X"
- "Сначала запланируем"
- "/plan <задача>"
- Задача меняет схему БД, интерфейс домена, security-чувствительный код
- Задача затрагивает несколько слоёв или несколько доменов
- Юзер не уверен в требованиях — план превращает разговор в письменный артефакт

## Когда НЕ применять

- Атомарная задача (правка одного файла, добавление одного теста, опечатка). План — overhead, который дороже самой работы.
- **Багфикс — НИКОГДА не `plan`.** Любой фикс (понятный или нет) → skill `triage-failure` (строгая петля RED→GREEN→REFACTOR). План для багфикса — анти-паттерн. Исключение — research-spike, когда корневая причина неясна после ≥2 попыток (тогда план именно на spike, не на фикс).
- Юзер уже дал готовый список шагов — записать в `<slug>.md` без декомпозиции.

## Жизненный цикл плана

```
PLANNING        — собираем контекст, задаём вопросы, пишем атомы
  ↓ (юзер approve)
IN-PROGRESS     — выполняем атомы, помечаем done с evidence
  ↓ (atoms закрылись или возникли новые вопросы)
CHECKPOINT      — сверяемся с реальностью, возможно перепланируем
  ↓
DONE            — все атомы зелёные, slug.md удаляется сразу (история в git log)
```

## Шаги

### 1. Понять задачу до того как писать план

Прочитай постановку. Если что-то неоднозначно — спрашивай **до** записи плана. План на догадках хуже, чем разговор.

Минимум 3-5 вопросов из этого списка (выбирай релевантные):

**Скоуп**
- Что входит в задачу? Что НЕ входит?
- Это новая фича / рефакторинг / багфикс / эксперимент?
- Связано ли с другими PR/тикетами?

**API / контракты**
- Меняем ли существующий API? Breaking change?
- Какая форма ответа? Коды ошибок?
- Идемпотентность нужна?
- Пагинация / фильтры / сортировка?

**Схема данных**
- Меняем ли схему БД?
- Прямая совместимость со старым форматом нужна?
- Нужен ли backfill / data migration?
- Индексы / FK / cascade?

**Cross-domain**
- Какой домен владеет логикой?
- Нужны ли новые порты / адаптеры?
- depguard допустит без правок?

**Безопасность**
- Кто имеет право вызывать? Authorizer-метод нужен?
- Чувствительные данные в логах / outbox?
- Audit-эвент нужен?

**Интеграции**
- Outbox-эвент эмитится? Кто consumer?
- Внешние API? Idempotency key?

**Тесты**
- TDD для какого слоя?
- Integration test нужен?
- Fuzz / bench?

**Rollout**
- Feature-flag нужен?
- Поэтапный rollout или сразу?

**Откат**
- Что делать если падает в проде?
- Down-миграция реально откатывает?

Если юзер на 5+ вопросов отвечает "не знаю / решай сам" — это сигнал, что задача недозрелая. Предложи отложить или сначала research-spike.

### 2. Сгенерировать slug

`<verb>-<object>[-<qualifier>]`, kebab-case, 2-4 слова, без даты:
- `refresh-rotation-race`
- `add-payment-domain`
- `migrate-user-status-enum`
- `bump-pgx-v6`

Проверь, что `.claude/plans/<slug>.md` ещё не существует. Если есть — добавь суффикс `-v2`.

### 3. Записать `.claude/plans/<slug>.md`

Шаблон ниже. Все секции обязательны кроме "Открытые вопросы" (если действительно ничего не висит).

```markdown
# <Понятный заголовок>

**Slug:** `<slug>`
**Создан:** <YYYY-MM-DD>
**Статус:** planning
**Последний чекпоинт:** —

## Контекст

<2-5 предложений: зачем эта задача, что уже известно, что уже пробовали.
Включая ссылки на код file:line, на коммиты, на закрытые тикеты.>

## Не входит в скоуп

- <что осознанно не делаем — тоже важно зафиксировать>

## Открытые вопросы

- [x] Q1: <вопрос> → <ответ юзера>
- [ ] Q2: <не закрытый вопрос — блокирует какие атомы?>

## Атомы

<Стандарт атома (валидируется `make plan-check`):
 - Ровно 1 коммит-worth работы (≤1 файл изменений в среднем; крупные — разбивай).
 - `Verify:` ОБЯЗАТЕЛЕН — конкретная команда (canonical make-верб) + ожидаемый результат.
 - `Зависит от:` явно (атом/слаг или —).
 - По закрытии — строка `**Done:**` с evidence (коммит-хеш / `make check → PASS` / `curl → 201`).
 Лимит ~15 атомов. Большой план группируй по фазам `### Phase N — <name>`
 (чекпоинт на границе фазы). >15 атомов — задача слишком крупная: разбей на
 2+ зависимых плана через roadmap `(after <slug>)`.>

### Phase 1 — <name>   (фазы — для больших планов; мелкий план — без фаз)

- [ ] **A1:** <короткое описание>
  - Что делаем: <1-2 строки>
  - Файлы: `path/to/file.go`, `migrations/00NN_*`
  - Verify: `make test PKG=./internal/domain/X` → PASS
  - Зависит от: —

- [ ] **A2:** ...
  - Что делаем: ...
  - Verify: `make check` → green
  - Зависит от: A1

## Infra impact

<Заполняется когда атом задевает инфра-поверхность (см. `.claude/rules/infra-impact.md`).
Каждая запись — INFRA-HANDOFF-айтем (WHAT/WHY/ACTION/WHO/DECIDE/RISK). `make release`
агрегирует эту секцию. План forward-only и удаляется по закрытии — поэтому
любой айтем обязан переехать в release-handoff ДО закрытия плана; не доехавший
до релиза — строкой в `roadmap.md ## Active`.>

—

## Чекпоинты

<Заполняется по мере работы. Каждая запись — что закрыто, что обнаружено, что переоценил.>

—
```

### 4. Зарегистрировать в `.claude/plans/roadmap.md`

Если файл не существует — создай:

```markdown
# Roadmap

План удаляется сразу по завершении — история остаётся в `git log`. Индекс не держит секцию завершённого. Открытый follow-up из закрытой задачи переезжает строкой в `## Active`.

## Active

- [<slug>](./<slug>.md) — <одна строка с сутью> — `planning` 0/N atoms
- [<slug-b>](./<slug-b>.md) — <суть> — `planning` 0/M atoms (after <slug>)

## Backlog (idea state)

- <идея без атомов: что и зачем, триггер когда заводить> — пока не план
```

Межплановая зависимость — суффикс `(after <slug>)` в строке Active: план-B не
стартует, пока `<slug>` не DONE. `## Backlog` — idea-state: дальние задачи без
атомов (чтобы не терялись); промоушн в Active = прогон через skill `plan`.

Если существует — добавь строку в Active (с `(after …)` если зависит).

### 5. Стоп. Покажи план юзеру.

Не начинай выполнение. Покажи:
- Путь к `<slug>.md`
- Краткое резюме (3-5 строк)
- Открытые вопросы, если остались
- Спроси: "Approve и поехали? Или ещё подумать?"

Юзер может: approve / поправить план / задать встречный вопрос / отложить.

### 6. Approve → IN-PROGRESS

Поменяй в `<slug>.md`: `Статус: in-progress`. Обнови строку в roadmap (`planning` → `in-progress`).

Дальше — иди по атомам. На каждый закрытый атом:
- Помечай `[ ]` → `[x]`
- Добавляй строку `**Done:** <evidence>` под атомом: коммит-хеш / `make check → PASS` / `curl … → 201` + одна фраза что именно сделано/обнаружено
- Если атом задел инфра-поверхность — занеси INFRA-HANDOFF-айтем в `## Infra impact` (skill `infra-handoff`)
- Обнови счётчик в roadmap (`X/N atoms`); большой план — отмечай границы фаз
- Чекпоинт-триггеры — см. §7; на границе фазы чекпоинт обязателен

### 7. Чекпоинты

Триггеры для чекпоинта:
- Закрыто 3+ атома подряд
- Появился новый открытый вопрос
- План оказался неверным (нашли что A2 на самом деле зависит от A4)
- Юзер вернулся после паузы и хочет сверки

В секцию `## Чекпоинты` добавляй запись:

```
### <YYYY-MM-DD HH:MM>
- Закрыто: A1, A2, A3 ✓
- Обнаружено: <неочевидное>
- Переоценил: A5 теперь блокирован Q3 → новый вопрос в Открытых
- Следующий шаг: A4
```

### 8. DONE

Когда все атомы зелёные:
1. **`## Infra impact` не пуст и ещё не релизился?** Айтемы обязаны доехать до infra-стороны: либо релиз состоялся (`make release` их сагрегировал), либо перенеси их строкой в `roadmap.md ## Active` как follow-up. Удалять план с несданным infra-impact нельзя.
2. Удали строку `<slug>` из `## Active` в roadmap. Если был `(after <slug>)` у другого плана — он разблокирован, отметь.
3. Удали `<slug>.md` — история уже в `git log` и коммитах. Никакой секции «выполненных» roadmap не держит.
4. Незакрытый follow-up (вкл. несданный infra-impact) переезжает отдельной строкой в `## Active`, а не остаётся хвостом в удаляемом плане.
5. Сообщи юзеру: задача закрыта, план удалён.

## Что планировщик делает дотошно

- Спрашивает до того как писать. План на догадках бесполезен.
- Атомы — реально атомарные. Если "A1: реализовать новый домен" — это не атом, это план в плане. Дроби.
- Verify-команда есть у каждого атома (canonical make-верб). Без неё непонятно, когда атом закрыт. `make plan-check` это валидирует.
- Зависимости явные. Если A2 после A1 — записано. Межплановые — `(after <slug>)` в roadmap.
- Не входит в скоуп — отдельная секция. Это дисциплинирует.
- Большой план — фазы + чекпоинт на границе фазы. Лимит ~15 атомов; больше — split.
- Атом задел инфру — `## Infra impact` заполняется сразу, не «потом» (доедет до release).

## Что планировщик НЕ делает

- ❌ Не пишет план "из головы" пропустив вопросы — запрос вопросов перед планом обязателен.
- ❌ Не обещает атомов больше ~15 в одном плане. До 15 — допустимо, но группируй по фазам с чекпоинтами. >15 — задача слишком крупная: разбей на 2+ плана с явной зависимостью `(after <slug>)` в roadmap.
- ❌ Не правит код в фазе planning. Только roadmap.md и slug.md.
- ❌ Не сам решает спорные дизайн-вопросы. Спрашивает.
- ❌ Не игнорирует существующий план — если `.claude/plans/<slug>.md` уже есть и in-progress, продолжай его, не создавай параллельный.

## Восстановление после /clear

Если новая сессия и юзер сказал "продолжаем":
1. `ls .claude/plans/` — есть ли активные slug.md?
2. Прочитай `roadmap.md` — какие в `Active` и в каком статусе?
3. Прочитай конкретный `<slug>.md` — последний чекпоинт, незакрытые атомы.
4. Сверься с git log с момента последнего чекпоинта — что реально произошло, что план не отразил?
5. Сделай чекпоинт-запись с обнаруженным расхождением, если есть.
6. Продолжай со следующего открытого атома.

План — это контракт между тобой-сейчас и тобой-через-неделю. Пиши так, чтобы тебя-через-неделю мог продолжить с пол-оборота.
