# Skill: smartdev (cockpit)

Каноничный entry-point. Не «показать сводку и замолчать», а **вести**: за один проход собрать состояние, поднять контекст, и **самому переключить** в правильный режим работы. Если упёрлось в drift/красное/инфра — не описывай, а чейни в нужный skill.

## Когда применять

- Начало сессии, после `/clear`, возврат после паузы
- Юзер дал задачу (сам или через хаб `<org>/infra`), но непонятно, насколько она большая
- Не уверен, какой режим сейчас правильный

## Когда НЕ применять

- Узкая чёткая задача ("поправь typo в X") — иди прямо в работу (RED→GREEN всё равно по дефолту)
- Уже идёт активная сессия с известным контекстом — не повторяй briefing

## Шаги

### 1. Собрать состояние

```bash
make status
```

(`make status A=--full` — добавит lint count, +~10s; только если нужен lint-обзор.)

Парси секции: `== Branch ==`, `== Working tree ==`, `== Critical ==` (BUILD/SQLC/MIGRATIONS/STACK-DRAFTS), `== Infra-touch ==`, `== Plan ==` (активные планы: статус, прогресс шагов и критериев, **следующий шаг**; число пунктов бэклога), `== Domains ==`, `== Recent commits ==`, `== TODOs in changed files ==`. Последняя строка — `OK` или `ATTENTION:<что>`: это твой сигнал ветвления.

### 2. Поднять контекст (фикс «не помнит») — читай сам, не жди скрипта

`make status` даёт детерминированный **детект критичного** (build/drift/infra/ATTENTION) — это сигнал ветвления, не вся картина. Ориентацию по проекту добери **чтением файлов** (status их намеренно не парсит — bash хрупок на прозе):

- **Бэклог — `.claude/plans/backlog.md`.** Если активных планов нет, **назови юзеру самые весомые пункты бэклога** как кандидатов «с чего начать», не молчи про них.
- **Активный план** (`== Plan ==` дал `<slug> · in-progress · … · дальше: S<N> — …`) — прочти `.claude/plans/<slug>.md` целиком, начиная с «Где мы сейчас». Продолжаешь с него, не с нуля и не перепланируя.
- **Что это за сервис** (свежая сессия / непонятно) — добери на месте, лениво: `go.mod` (module path → де-темплейтизирован форк или ещё канон-шаблон?), `docs/stack/` (стек, что `draft`, что `stable`; домены — в соседнем strategy-репо `../strategy`), наличие reference-доменов `auth`/`user`/`verification` (на месте → форк ещё «помнит» шаблон, путь — `/init-service`).
- Договорённости прошлых сессий живут в закоммиченных артефактах (планы с их «Где мы сейчас», CLAUDE.md, rules) — там сверяйся; авто-память в шаблоне не используется.

Это on-demand: контекст уже подняли в этой сессии — не перечитывай.

### 3. Чейнить (фикс «не ведёт дальше») — не описывай, переключай

По приоритету сверху вниз. Первое сработавшее — переключаешься туда **сразу**, говоришь юзеру «→ перехожу в `<skill>`, потому что <причина>»:

| Сигнал из status / задачи | Действие — чейн |
|---|---|
| `ATTENTION:` build / sqlc-drift / красный тест | → `triage-failure` (red-арм, RED→GREEN разбор) |
| `== Infra-touch ==` не `none` (или правишь env/секрет/миграцию/cross-service/go.mod) | → `infra-handoff` (оформить INFRA-HANDOFF до claim/коммита) |
| Активный план `in-progress` | Продолжай со следующего открытого шага; перед остановкой обнови «Где мы сейчас» (skill `plan`) |
| Юзер дал задачу, big (меняет схему/интерфейс/security, >5 шагов, >1 слой) | → `plan` (декомпозиция; planner спрашивает, не угадывает) |
| Задача = скаффолд (домен/endpoint/event/port/миграция) | → `scaffold` (вариант по типу блока) |
| Багфикс (любого размера) | → `triage-failure` (TDD red-first; **не** `plan`) |
| Задача мелкая и понятная | Делай напрямую — но по RED→GREEN (см. §4) |
| Пусто (нет задачи, нет плана, всё зелёно) | Спроси юзера какую задачу решаем |

### 4. RED→GREEN→REFACTOR — дефолтная петля, не исключение

Любое изменение кода по умолчанию:

1. **RED** — сначала тест, выражающий желаемое/баг. Запусти `make test PKG=./<pkg>/...` → убедись, что red, и red **по той причине**.
2. **GREEN** — минимальная правда продакшен-кода до зелёного.
3. **REFACTOR** — чистка при зелёном; `make test` держит зелёным.
4. Перед claim «готово» — `make check`.

Багфикс — строгий случай этой петли, его ведёт `triage-failure`. Фича — та же петля, тест-first. Отступление от RED→GREEN — осознанное решение, проговори его юзеру.

### 5. Передача в planner

Нужен план — не делай его в smartdev. Чейнь в `plan` с задачей+контекстом. Planner — отдельная процедура с дотошными вопросами.

## Формат вывода

Сводка — картина, которую юзер схватывает с одного взгляда, + явный переход:

```
## Состояние
**Ветка:** `<branch>` <ahead/behind>
**Critical:** BUILD ok · SQLC ok · MIGRATIONS ok · STACK-DRAFTS none   (или ATTENTION:<...>)
**Infra-touch:** none / <файлы>
**План:** `<slug>` in-progress → дальше S<N>  (или —)

## Что висит
- <главное из TODO / непарных миграций / draft>

## Идеи в бэклоге (если активных планов нет)
- <самые весомые пункты `.claude/plans/backlog.md` — кандидаты «с чего начать»>

## → Перехожу в <skill> / Продолжаю план с S<N>
<одна фраза почему>
```

Блок «Идеи в бэклоге» показывай, когда активного плана нет: дай юзеру зацепку, не оставляй пустой экран. Есть активный план — этот блок опускай.

Если юзер дал задачу — после сводки сразу §3 (оценка+чейн) одним абзацем.

## Что smartdev НЕ делает

- Не гонит `make check` целиком сам (это перед claim «готово» / коммитом, или явная просьба).
- Не делает edits/коммитов в фазе briefing.
- Не `git pull`/`fetch` без явной просьбы.
- Не перепланирует активный план — продолжает его.

## Anti-patterns

- ❌ Дамп raw `make status` в чат. Сводка — резюме, не сырьё.
- ❌ Длинный briefing — юзеру нужна картина с одного взгляда и следующий шаг.
- ❌ Описать проблему и остановиться («есть drift»). Cockpit **переключает**, а не комментирует.
- ❌ Перепланировать вместо продолжения активного плана.
- ❌ Багфикс через `plan`. Багфикс → `triage-failure`, RED-first.
- ❌ Игнорить `== Infra-touch ==`.
- ❌ `make status A=--full` без причины (+10s, ничего не меняет если нет lint-вопроса).
