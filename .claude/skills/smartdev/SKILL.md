# Skill: smartdev

Каноничный entry-point для работы с этим репозиторием. Цель — за один проход дать полную картину "что сейчас происходит" и переключить в правильный режим работы (немедленно делать / планировать / разбираться с drift).

## Когда применять

- В начале сессии: "/smartdev", "что у нас", "с чего начать"
- После /clear или возврата к репо после долгой паузы
- Когда юзер сформулировал задачу, но непонятно насколько она большая
- Перед коммитом — для финального state-check (но это пересечение с `run-pre-merge`, выбирай по контексту)

## Когда НЕ применять

- Юзер уже дал чёткую узкую задачу ("поправь typo в X") — иди прямо в работу
- Уже идёт активная сессия с известным контекстом — не надо повторять briefing

## Шаги

### 1. Собрать сводку

```bash
scripts/agent-tools/status.sh
```

(Или `--full` если у юзера есть терпение на ~10s — добавит lint/sqlc-diff/mocks-check.)

Парси секции:
- `== Branch ==` — где стоим, есть ли drift с remote
- `== Working tree ==` — что недокоммичено
- `== Plans ==` — есть ли активный план
- `== Domains ==` — общая картина бизнес-доменов
- `== Migrations ==` — последний номер, нет ли непарных up/down
- `== Recent commits ==` — что было недавно
- `== TODOs ==` — что висит

### 2. Если задача от юзера уже сформулирована — оцени её размер

| Признаки | Действие |
|---|---|
| Меньше 5 атомарных шагов, без неочевидностей | Иди делать. План не нужен. |
| Меняет схему БД / интерфейс домена / security-чувствительный код | Активируй skill `plan`. Сначала планирование, потом работа. |
| Затрагивает >1 файла за пределами одного слоя | План рекомендован. Спроси юзера: "план или сразу делать?" |
| Юзер сам сказал "распиши план" или подобное | Skill `plan`. |

### 3. Если задачи нет — предложи следующее действие на основе сводки

Приоритеты (сверху вниз):
1. **DRIFT в сгенерированном коде** (sqlc-diff/mocks-check FAIL) — починить раньше, чем что-то ещё. `make sqlc` / `make mocks`.
2. **Активный незакрытый план** (`.claude/plans/<slug>.md` со status=in-progress) — продолжить с последнего чекпоинта.
3. **Незакоммиченные изменения** — спросить, нужен ли коммит / pre-merge.
4. **Пустое state** — спросить юзера какую задачу решать.

### 4. Формат вывода

Один markdown-блок ≤30 строк:

```
## Состояние

**Ветка:** `<branch>` <ahead/behind>
**Working tree:** N modified, M untracked
**Активный план:** <slug или "—">
**Drift:** sqlc=OK, mocks=OK (или DRIFT)

## Свежие коммиты
- <hash> <subject> (<ago>)
- ...

## Что висит
- <TODO/FIXME из changed-files, max 3>
- <непарные миграции, если есть>

## Предлагаю
<одно конкретное действие на основе приоритетов выше>
```

Если юзер сразу дал задачу — после сводки переходи к её оценке (см. шаг 2) одним абзацем.

### 5. Передача в planner

Если решил, что нужен план — не делай его сам в smartdev. Вызывай skill `plan` с задачей и контекстом. Planner — отдельная процедура с дотошными вопросами.

## Что не делает smartdev

- Не запускает `make pre-merge` целиком (это работа `run-pre-merge` skill'а или явной команды юзера).
- Не делает edits / коммитов сам.
- Не ходит в `git pull` / `fetch` без явного запроса — у юзера может быть рабочее состояние, которое он не хочет трогать.
- Не читает чужие домены без причины — сводка из `status.sh` достаточна для overview.

## Anti-patterns

- ❌ Дамп всего вывода `status.sh` в чат. Сводка — твоё резюме, не raw.
- ❌ Briefing на 100 строк. Юзер хочет 30-секундную картину, не лекцию.
- ❌ Запуск `--full` без причины — это +10s и ничего не меняет, если drift'ов нет.
- ❌ Сразу прыгать в plan-skill, минуя оценку размера. На "поправь typo" план не нужен.
